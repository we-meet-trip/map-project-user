# 트러블슈팅과 교훈 (map-project-user)

개발하면서 실제로 겪은 문제를 증상·원인·해결·검증·교훈 순서로 적는다. 커밋 링크는 공개 히스토리의 해당 커밋이다.

---

## T-CI-01 부팅까지 하는 테스트가 CI 에서만 실패한다
- **증상**: 개발 기기에서는 통과하는 애플리케이션 컨텍스트 테스트 몇 개가 푸시할 때마다 CI 에서 실패했다.
- **원인**: 컨텍스트가 뜰 때 Redis Streams 구독을 시작하는데, 개발 기기에는 대개 Redis 가 떠 있고 CI 러너에는 없었다. 원인이 코드에 없어 찾기 어려웠다.
- **해결**: CI 잡에 Redis 서비스 컨테이너를 띄운다(`.github/workflows/ci.yml`).
- **검증**: CI 의 test 잡이 Redis 서비스를 띄운 채 전체 테스트를 돈다(`ci.yml`).
- **교훈**: "내 기기에서는 된다" 는 테스트가 기대는 외부 프로세스를 먼저 의심한다. 테스트가 필요로 하는 것은 CI 정의에 드러나 있어야 한다.
- **관련 커밋**: [`15fbd23`](https://github.com/we-meet-trip/map-project-user/commit/15fbd235eaeaf93cdf63bdef36765f6f1273ec18)

## T-BUILD-01 손에서 통과한 빌드가 이미지 안에서 다른 도구로 만들어진다
- **증상**: 로컬 Gradle 래퍼와 Docker 빌드 단계의 Gradle 판이 달라(8.12.1 과 8.12), 같은 소스가 두 곳에서 다른 도구로 빌드됐다.
- **원인**: `Dockerfile` 의 `FROM gradle:<판>` 과 `gradle-wrapper.properties` 를 따로 관리했다.
- **해결**: 둘을 맞추고, CI 에 두 판이 같은지 비교하는 단계를 넣었다.
- **검증**: CI 의 '만드는 판이 래퍼와 같은가' 단계가 두 판이 다르면 실패한다.
- **교훈**: 같은 사실을 두 곳에 적어야 하면 둘이 같은지 기계가 확인하게 한다.
- **관련 커밋**: [`9806695`](https://github.com/we-meet-trip/map-project-user/commit/9806695f82755b956aad7d27a4306d4bd564cf7b)


## T-CHAT-01 패턴 목적지로 남의 방 대화를 함께 받는다
- **증상**: 참가하지 않은 방의 메시지가 한 번의 구독으로 함께 들어왔다.
- **원인**: 구독 목적지 검사가 `*`·`?` 만 막고 있었는데, 브로커는 목적지를 경로 패턴으로 해석한다. `/topic/{a}/{b}` 는 두 글자 어느 것도 없어 검사를 통과했고, 방 토픽 접두어로 시작하지도 않아 참가자 확인도 건너뛰었다.
- **해결**: 목적지 판정을 브로커가 쓰는 것과 같은 경로 대조기에 맡겼다. 새 패턴 문법이 생겨도 함께 막힌다.
- **검증**: 패턴 목적지로 구독하는 테스트가 거절된다.
- **교훈**: 보안 검사를 직접 구현한 문자열 규칙으로 하지 말고, 실제로 그 값을 해석하는 구성 요소와 같은 해석기를 쓴다.
- **관련 커밋**: [`cbc118a`](https://github.com/we-meet-trip/map-project-user/commit/cbc118a86bd73a22a360bb2c0261d8594d5a5f9b)

## T-CHAT-02 유휴 연결이 조용히 끊기고 메시지가 사라진다
- **증상**: 이동통신망에서 한동안 말이 없던 채팅 연결로 보낸 메시지가 화면에만 남고 상대에게 가지 않았다.
- **원인**: 브로커에 하트비트용 스케줄러를 주지 않아 접속 응답의 하트비트가 `0,0` 으로 협상됐다. 중간 장비가 오가는 것 없는 연결을 걷어가도 양쪽 다 모르고, 보내는 쪽은 연결됐다고 믿어 REST 로 되돌아가지도 않았다.
- **해결**: 브로커에 스케줄러를 붙여 하트비트를 `10000,10000` 으로 맞췄다.
- **검증**: 실제 접속 응답에서 하트비트 값이 `0,0` 에서 `10000,10000` 으로 바뀐 것을 확인했다(자동 테스트는 없다).
- **교훈**: 연결 유지 장치는 설정했다고 믿지 말고 실제로 협상된 값을 본다.
- **관련 커밋**: [`bb01eb1`](https://github.com/we-meet-trip/map-project-user/commit/bb01eb1bf89596c4fbd9d16370c86f6c9a511efe)

## T-TRIP-01 일정 생성이 사유 없이 실패한다
- **증상**: 오래 걸린 일정 생성이 서버가 준비한 시간초과 안내 없이 그냥 실패로 보였다.
- **원인**: 대기 상한을 앱 > 서버 순서로만 맞췄는데, 그 사이의 앞단 프록시가 서버보다 짧게(120초) 기다렸다. 서버 상한(150초)은 이 경로에서 닿을 수 없는 값이었다.
- **해결**: 서버 상한을 110초로 낮춰 서버가 먼저 포기하고 사유를 돌려주게 했다(`USER_TRIP_POLL_TIMEOUT_SECONDS`).
- **검증**: 평상시 완료(수 초)에는 영향이 없음을 확인.
- **교훈**: 시간 제한은 사슬 전체(앱 > 앞단 > 서버 > 작업자)를 한 줄로 놓고 정한다.
- **관련 커밋**: [`26d6224`](https://github.com/we-meet-trip/map-project-user/commit/26d6224a8f4e59b047029bceb5d0a72756cf5163)

## T-TRIP-02 방문지가 많은 일정은 도로 경로가 전부 직선이다
- **증상**: 방문지가 22곳을 넘는 일정은 화면의 이동선이 모두 직선이었다. 오류 표시는 없었다.
- **원인**: hub 의 길찾기 묶음 요청은 구간 20개까지 받는데, user 가 나누지 않고 한 번에 보내 요청 전체가 거절됐다. 거절되면 직선으로 대신 그리도록 되어 있어 조용히 넘어갔다.
- **해결**: 20개씩 나눠 보내고 원래 순서로 합친다. 한 묶음이 실패해도 그 구간만 비운다.
- **검증**: 구간 20개 묶음 하나가 시간 제한 안에서 한 번만 요청되는지 보는 테스트.
- **교훈**: 대체 동작(fallback)이 있으면 실패가 보이지 않는다. 대체 동작을 탈 때는 로그만이 아니라 지표나 응답에도 남긴다.
- **관련 커밋**: [`02c9d6f`](https://github.com/we-meet-trip/map-project-user/commit/02c9d6fb246cc9a27a3b5eff543c172d1b090fb4)

## T-TRIP-03 이동수단을 대문자로 보내면 경로만 빠진다
- **증상**: 요청은 200 이고 일정도 나오는데 도로 경로만 빠져 직선이 됐다.
- **원인**: 도로 경로를 물을지 판정할 때 소문자 이동수단만 받았다. 캐시 키는 이미 표기를 하나로 맞추고 있어 그곳만 어긋났다.
- **해결**: 판정 전에 표기를 맞추고, 받는 쪽(소문자만 받는다)에 넘기는 값도 맞춘다.
- **검증**: 대문자 이동수단 테스트, 버스는 여전히 묻지 않는다는 회귀 테스트.
- **교훈**: 입력 정규화는 한 곳에서 한 번 한다.
- **관련 커밋**: [`159e8d7`](https://github.com/we-meet-trip/map-project-user/commit/159e8d70c96bbc69827dbe3944b413a6e48cd5de)

## T-REC-01 같은 조건 동시 요청이 agent 를 중복으로 부른다
- **증상**: 같은 지역·조건을 여러 사람이 동시에 요청하면 모두 캐시 미스로 판정돼 각자 agent 를 불렀다. 요청 하나가 모델을 두 번 쓰므로 비용이 그대로 배가 됐다.
- **원인**: 재사용 캐시 조회가 평범한 읽기였다.
- **해결**: `SET NX` 로 만드는 쪽 하나만 정하고 나머지는 그 실행에 붙인다. 붙는 쪽도 자기 `job_id` 를 새로 받는다 — 앞선 작업을 그대로 주면 한 사람의 편집이 다른 사람 결과를 바꾼다.
- **검증**: 동시 요청·실행 세대 격리 테스트(`RecommendFollowerIsolationTest`).
- **교훈**: 캐시는 '있으면 쓴다' 만으로는 비용을 막지 못한다. 만드는 중인 것도 공유해야 한다.
- **관련 커밋**: [`335b389`](https://github.com/we-meet-trip/map-project-user/commit/335b3894570c4856b84082cac8c15636bc4ec116)

## T-REC-02 학습 신호가 조용히 사라진다
- **증상**: 추천은 정상으로 보이는데 PostgreSQL 완료 기록과 학습 신호가 가끔 빠져 있었다.
- **원인**: 스트림 소비자가 PostgreSQL 기록 실패를 삼킨 뒤 그대로 ack 해서 메시지가 없어졌다. 사용자는 Redis 초안으로 결과를 이미 받으므로 아무도 눈치채지 못했다.
- **해결**: 기록이 실패하면 ack 하지 않는다. 메시지는 PEL 에 남아 다시 회수되고, 재시도가 다하면 DLQ 로 간다. 연결고리를 읽으면서 지우는(GETDEL) 캐시 갱신은 기록 뒤로 옮겼다.
- **검증**: 기록 실패 시 ack·연결고리 소비가 일어나지 않는 테스트.
- **교훈**: ack 는 '처리했다' 가 아니라 '잃어도 된다' 는 선언이다. 영속 기록이 끝난 뒤에만 한다.
- **관련 커밋**: [`949df68`](https://github.com/we-meet-trip/map-project-user/commit/949df68f6a00812d67b440300f69ba09e34eac88)

## T-REC-03 끝난 추천이 진행 중으로 되돌아가 무한 대기한다
- **증상**: 드물게 완료된 추천의 조회가 계속 202(진행 중)였다.
- **원인**: 완료 기록이 접수 기록보다 먼저 도착하면, 늦게 온 접수 기록이 같은 행을 진행 중으로 덮었다.
- **해결**: 같은 `job_id` 가 있으면 접수 기록을 무시한다. 존재 확인과 삽입 사이의 경합(무결성 위반)도 같이 처리한다.
- **검증**: 완료가 먼저 오는 순서의 테스트.
- **교훈**: 비동기 이벤트는 순서를 보장받지 못한다. 상태 전이는 '앞으로만' 가게 만든다.
- **관련 커밋**: [`081b01c`](https://github.com/we-meet-trip/map-project-user/commit/081b01c6f2faf190b7343adb0aa29c87b7e7d23e)

## T-STREAM-01 Redis 가 잠깐 끊긴 뒤 결과 소비가 영영 멈춘다
- **증상**: Redis 에 일시적인 시간초과가 난 뒤 추천 결과가 더 들어오지 않아, 동기 일정 생성이 모두 시간초과가 됐다.
- **원인**: 스트림 폴링 작업이 명령 시간초과로 죽은 뒤 구독이 다시 살아나지 않았다. 폴링 대기(2초)와 명령 시한이 가까워 일시 지연에도 죽기 쉬웠다.
- **해결**: 구독이 멈췄는지 10초마다 보고 다시 구독하는 워치독을 두고, 스트림 전용 명령 시한을 폴링 대기보다 넉넉하게(6초) 잡았다.
- **검증**: 구독이 비활성일 때 다시 구독하는 테스트.
- **교훈**: 오래 사는 구독은 죽는다고 가정하고, 살아 있는지 확인하는 장치를 따로 둔다.
- **관련 커밋**: [`90e6990`](https://github.com/we-meet-trip/map-project-user/commit/90e6990f9d0f90d1e38dd141c5a293e5c4d17625)

## T-SEC-01 요청 한도의 기준 주소를 요청자가 정할 수 있다
- **증상**: 로그인 같은 인증 경로의 요청 한도가, 요청자가 주소 헤더 값을 바꿔 가며 보내면 우회됐다.
- **원인**: 주소 헤더를 직전 발신자와 무관하게 믿었다.
- **해결**: 직전 발신자가 신뢰 프록시 대역(`USER_RATELIMIT_TRUSTED_PROXIES`)일 때만 헤더를 읽고, 그 밖에서는 실제 발신 주소를 쓴다. 값이 여러 개 이어질 수 있는 `X-Forwarded-For` 대신 앞단이 늘 덮어쓰는 `X-Real-IP` 를 본다.
- **검증**: 이 변경을 묶는 자동 테스트는 아직 없다(남은 과제).
- **교훈**: 클라이언트가 정할 수 있는 값을 보안 판정의 키로 쓰지 않는다.
- **관련 커밋**: [`9354225`](https://github.com/we-meet-trip/map-project-user/commit/9354225f51f6571274da0673a22f55c989484b4f)

## T-REC-04 재탐색 하루 한도를 새 작업으로 우회할 수 있다
- **증상**: 재탐색 한도가 일정·작업 단위로 세어져, 새 추천 작업을 만들면 한도가 다시 찼다.

- **교훈**: 한도는 '누가 쓰는가' 로 센다. 사용자가 새로 만들 수 있는 식별자로 세면 우회된다.

## T-REDIS-01 재사용 캐시가 채팅 키와 같은 논리 DB 를 쓴다
- **증상**: 재사용 캐시 기본 DB 번호가 채팅 접속 상태와 같은 5번이었다.
- **원인**: 통합 실행 설정이 5번을 채팅용으로 이미 정해 두었는데 이 서비스의 기본값이 그것을 몰랐다.
- **해결**: 재사용 캐시를 6번으로 옮겼다.
- **검증**: 설정 기본값 변경이며 자동 테스트는 없다.
- **교훈**: 공유 자원(Redis 논리 DB, 포트)의 배정표는 한 곳에 두고 서비스 기본값을 그 표에 맞춘다.
- **관련 커밋**: [`9fc818e`](https://github.com/we-meet-trip/map-project-user/commit/9fc818e5c6d9db3791da32d07b342e67a9eb98ca)

## T-WEATHER-01 재추천 뒤에도 같은 날씨 알림이 되살아난다
- **증상**: 날씨 변화 알림을 보고 재추천을 눌러도 30분 뒤 같은 알림이 다시 붙었다.
- **원인**: 재추천이 알림만 지우고 기준선은 저장 시점 예보로 두었다. 기준선이 옛 예보인 한 차이가 그대로 남아 순회가 같은 변화를 매번 새로 찾았다.
- **해결**: '알고 행동했다' 는 점에서 무시와 재추천은 같으므로, 둘 다 기준선을 지금 예보로 옮긴다.
- **검증**: 재추천 뒤 다음 순회에서 알림이 다시 붙지 않는 테스트.
- **교훈**: 알림을 지우는 것과 알림의 원인을 해소하는 것은 다르다.
- **관련 커밋**: [`318d3cb`](https://github.com/we-meet-trip/map-project-user/commit/318d3cb941c467a963b5626ebd4eae6a36e33047)
